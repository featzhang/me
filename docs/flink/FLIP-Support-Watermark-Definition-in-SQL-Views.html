FLIP-XXX: Support Flexible Watermark Assignment via Built-in Function

  • Authors: FeatZhang (featzhang@apache.org)

Abstract

This FLIP proposes a new built-in table function APPLY_WATERMARK that enables users to explicitly assign or override watermark strategies on any relational input — including base tables, non-materialized views, and subqueries — as an expression within SQL queries.

This design is motivated by the community discussion on FLINK-39062, where Timo Walther and Lincoln Lee converged on a function-based approach as a clean alternative to embedding watermark definitions into CREATE VIEW / ALTER VIEW statements.

Motivation

Problem

Currently, watermarks in Flink SQL can only be defined at the CREATE TABLE level via the WATERMARK FOR ... AS ... clause. This creates significant limitations for real-world usage:

  • Broken Abstraction: Users who build layered data pipelines (Bronze/Silver/Gold medallion architecture) must reach down into the base table definition to configure watermarks, exposing implementation details.
  • No Flexibility for Multi-Tenancy: In multi-tenant scenarios, different consumers of the same source table may require different watermark strategies (e.g., different lateness tolerances for different SLAs), but there is no way to define per-query watermarks.
  • Limited Architecture Support: When users receive catalogs as given (e.g., in a shared data platform), they cannot write queries that establish event-time semantics without modifying the underlying table DDL.
  • SQL/DataStream API Gap: The DataStream API allows users to assign watermarks flexibly at any point in the pipeline. SQL users have no equivalent capability, creating a fundamental usability gap.

Community Feedback Summary

From the mailing list discussion:

  • Timo Walther (Confluent / PMC): Raised concerns about attaching watermark semantics directly to SQL views, as views are pure logical aliases and a watermark would introduce an optimization barrier or change the fundamental concept of a view. Agreed on the APPLY_WATERMARK PTF direction. Also noted that this would benefit from: (1) lambda expression support (Calcite upgrade in progress at Confluent), and (2) a new WatermarkFunction interface for user-defined PTFs.
  • Lincoln Lee (Alibaba): Proposed the APPLY_WATERMARK(table, DESCRIPTOR(col), expr) built-in function approach, initially scoped to base tables only. Agreed on the general direction.
  • Gyula Fóra (Ververica): Emphasized the need for watermarks to be applicable not just to base tables, but also to views and subqueries — consistent with how DataStream API users think about watermark assignment.
  • FeatZhang (Author): Proposed extending APPLY_WATERMARK to support both base tables and non-materialized views, keeping view semantics pure while enabling flexible watermark assignment via an explicit relational operator.

Goals

  • Introduce a built-in PTF APPLY_WATERMARK(table, DESCRIPTOR(rowtime_column), watermark_expression) that assigns or overrides a watermark strategy on a relational input.
  • Support base tables, non-materialized views, and subqueries as input to APPLY_WATERMARK.
  • Keep SQL views as pure logical abstractions — no changes to CREATE VIEW or ALTER VIEW semantics.
  • Ensure the function compiles to a specialized ExecNode in the physical plan (similar to VECTOR_SEARCH and ML_PREDICT), maintaining planner control over watermark semantics.
  • Lay groundwork for future user-defined watermark functions via a WatermarkFunction interface.

Non-Goals

  • This FLIP does not change the semantics of SQL views.
  • This FLIP does not introduce watermark metadata into the view catalog.
  • User-defined PTFs that emit watermarks are out of scope for this FLIP (tracked separately per Timo's suggestion).
  • Lambda expression syntax for watermark expressions is out of scope (depends on Calcite upgrade).

Proposed Changes

1. New Built-in Function: APPLY_WATERMARK

Syntax

APPLY_WATERMARK(table_or_view, DESCRIPTOR(rowtime_column), watermark_expression)

Parameters

Parameter

Type

Description

table_or_view

Table reference

Base table, view, or subquery providing the input rows

DESCRIPTOR(rowtime_column)

Column descriptor

The column to use as the rowtime attribute

watermark_expression

Scalar expression

Watermark strategy expression (e.g., rowtime - INTERVAL '5' SECOND)

Return Type

The function returns a table with the same schema as the input, but with the specified watermark strategy applied. The rowtime column becomes a proper rowtime attribute in the resulting relation.

Usage Examples

Example 1: Override watermark on a base table

SELECT *

FROM APPLY_WATERMARK(orders, DESCRIPTOR(order_time), order_time - INTERVAL '5' SECOND);

Example 2: Apply watermark on a non-materialized view

-- Silver view (no watermark defined)

CREATE VIEW silver_events AS

SELECT CAST(JSON_VALUE(raw_data, '$.event_time') AS TIMESTAMP(3)) AS event_time,

       JSON_VALUE(raw_data, '$.user_id') AS user_id

FROM bronze_events;

-- Consumer A: strict lateness tolerance

SELECT TUMBLE_START(event_time, INTERVAL '1' HOUR),

       COUNT(*)

FROM APPLY_WATERMARK(silver_events, DESCRIPTOR(event_time), event_time - INTERVAL '5' SECOND)

GROUP BY TUMBLE(event_time, INTERVAL '1' HOUR);

-- Consumer B: lenient lateness tolerance

SELECT TUMBLE_START(event_time, INTERVAL '1' HOUR),

       COUNT(*)

FROM APPLY_WATERMARK(silver_events, DESCRIPTOR(event_time), event_time - INTERVAL '30' SECOND)

GROUP BY TUMBLE(event_time, INTERVAL '1' HOUR);

Example 3: Apply watermark on a subquery

SELECT TUMBLE_START(ts, INTERVAL '1' HOUR),

       user_id,

       COUNT(*)

FROM APPLY_WATERMARK(

                       (SELECT user_id, CAST(event_ts AS TIMESTAMP(3)) AS ts

                        FROM raw_log), DESCRIPTOR(ts), ts - INTERVAL '10' SECOND)

GROUP BY TUMBLE(ts, INTERVAL '1' HOUR),

         user_id;

Example 4: Layered Data Architecture (Bronze/Silver/Gold)

-- Bronze: Raw ingestion (no watermark)

CREATE TABLE bronze_events (raw_data STRING, ingestion_time TIMESTAMP(3)) WITH (...);

-- Silver: Cleaned view (no watermark, pure SQL alias)

CREATE VIEW silver_events AS

SELECT CAST(JSON_VALUE(raw_data, '$.event_time') AS TIMESTAMP(3)) AS event_time,

       JSON_VALUE(raw_data, '$.user_id') AS user_id

FROM bronze_events

WHERE JSON_VALUE(raw_data, '$.event_time') IS NOT NULL;

-- Gold: Aggregation with explicit watermark assignment

SELECT TUMBLE_START(event_time, INTERVAL '1' HOUR) AS window_start,

       COUNT(*) AS event_count

FROM APPLY_WATERMARK(silver_events, DESCRIPTOR(event_time), event_time - INTERVAL '10' SECOND)

GROUP BY TUMBLE(event_time, INTERVAL '1' HOUR);

2. Planner Changes

Logical Plan

APPLY_WATERMARK translates to a new logical node LogicalWatermarkAssigner at query parse/validate time. The planner performs:

  • Input resolution: Resolves table_or_view to a RelNode (base scan, view expansion, or subquery).
  • Column validation: Validates that DESCRIPTOR(rowtime_column) refers to an existing column of TIMESTAMP or TIMESTAMP_LTZ type.
  • Expression validation: Validates that watermark_expression is a valid scalar expression referencing columns in the input schema, with monotonicity guarantees.
  • Watermark override: If the input already carries a watermark (e.g., from the base table definition), the APPLY_WATERMARK node overrides it.

Physical Plan

APPLY_WATERMARK compiles to a specialized ExecNode — similar to how VECTOR_SEARCH and ML_PREDICT are handled — ensuring that the planner retains control over watermark semantics and optimization barriers are introduced only where explicitly requested.

This means:

  • The surrounding plan is not affected by optimization barriers unless APPLY_WATERMARK is used.
  • Views themselves continue to dissolve transparently into the plan (via predicate pushdown, projection pushdown, etc.).
  • The watermark assignment is a first-class physical operator, not a hidden side effect.

Interaction with Existing Table Watermarks

Input has existing watermark?

Behavior

APPLY_WATERMARK overrides it

No

View (no watermark in catalog)

APPLY_WATERMARK introduces new watermark

3. Catalog Changes

No catalog changes are required. APPLY_WATERMARK is a query-level construct and does not persist watermark metadata into any catalog.

4. API Changes

No public Java/Scala API changes are required for this FLIP. The feature is exposed purely through SQL syntax.

5. Future Extension: WatermarkFunction Interface (Out of Scope)

As discussed by Timo, we could introduce a WatermarkFunction interface in the future that allows user-defined PTFs to emit watermarks. This would follow the same pattern as ChangelogFunction. This is explicitly out of scope for this FLIP but is noted as a natural follow-up.

Backward Compatibility

  • No breaking changes to existing SQL syntax.
  • Existing CREATE TABLE watermark definitions continue to work unchanged.
  • APPLY_WATERMARK is purely additive.

Test Plan

  • Unit tests: Validate SQL parsing, logical plan generation, and type checking for APPLY_WATERMARK.
  • Integration tests:
  • Base table input
  • View input (non-materialized)
  • Subquery input
  • Override of existing table watermark
  • Event-time window aggregation over APPLY_WATERMARK output
  • End-to-end tests: Full pipeline from source ingestion to windowed aggregation using APPLY_WATERMARK.
  • Regression tests: Ensure existing watermark behavior is not affected.

Rejected Alternatives

Alternative 1: CREATE VIEW ... WATERMARK FOR ...

The original proposal was to allow watermark definitions directly in CREATE VIEW statements. This was rejected because:

  • SQL views are pure logical aliases; adding watermark semantics would blur the conceptual boundary.
  • It would require introducing optimization barriers into view expansion.
  • It conflates logical abstraction (view) with physical planning (watermark assignment).

As Timo noted: "A view usually dissolves into the plan (e.g. via projection or filter pushdown). Would a watermark definition suddenly introduce an optimization barrier? If this is an optimization barrier, is this still a view or a new concept?"

Alternative 2: ALTER VIEW SET WATERMARK

This was rejected because:

  • It modifies view semantics by storing hidden physical properties in the catalog.
  • It creates implicit behavior that is invisible to the query reader.
  • Catalog-level watermarks on views have unclear propagation semantics when views are nested.

Open Questions

  • Lambda expression syntax: When Calcite lambda support lands (per Timo's roadmap at Confluent), should the watermark_expression be changed to a lambda? This would be a cleaner API but requires the Calcite upgrade first.
  • Scope of input support: Should APPLY_WATERMARK support only base tables and views, or also arbitrary subqueries? This FLIP proposes supporting all three, but the planner implications for subqueries need further review.
  • Interaction with VECTOR_SEARCH / ML_PREDICT pattern: Can we reuse the existing PTF infrastructure for specialized ExecNodes, or is a new extension point needed?
  • Naming: Is APPLY_WATERMARK the right name? Alternatives: ASSIGN_WATERMARK, WITH_WATERMARK, SET_WATERMARK.
